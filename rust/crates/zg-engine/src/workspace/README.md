# Workspace persistence

`workspace` connects domain workspace state to the filesystem. It owns the name registry, manifest encoding, physical index locations, build publication and recovery, and workspace locks. The domain owns `Workspace`, `ScanRules`, `IndexState`, `IndexDescriptor`, and `EmbeddingModelInfo`; the engine's `file_selection` capability implements scanning rules. API result views are assembled at the application boundary.

## Names and the registry

The manifest owns the workspace name, root, scan rules, model bindings and saved runtime settings. Names are validated, case-sensitive labels; different roots can share one name. New workspaces use the root basename unless the caller supplies `IndexOptions::name`, CLI `--name`, or MCP `name`. An explicit name updates the manifest only when indexing completes; renaming does not require a rebuild.

The per-user `workspaces.json` is an optional discovery cache keyed by root. It is updated after manifest publication. Missing global state, duplicate labels, or an inaccessible registry cannot block workspace operations. Read-only operations do not consult it. `ZVEC_GREP_WORKSPACE_REGISTRY` chooses an explicit cache file; otherwise an existing global directory is used without creating one for registration alone.

Move or copy the root together with `.zvec-grep` to retain settings and storage. Reads resolve source paths against the current root; saved model-cache and ignore-file paths inside the old root are also relocated. External paths remain external. The next successful index refreshes the optional discovery entry and removes a vanished previous location. A copy can keep the same name.

Explicit indexing API keys are represented by `EncryptedApiKey` in persisted `StoredModelConfig`, separate from runtime `ModelConfig`. XChaCha20-Poly1305 uses a random nonce and the model reference as authenticated data. `credentials.key` holds a random per-workspace key; environment/global credentials never enter persisted settings. The complete directory is portable but also sufficient to decrypt saved keys. Plaintext credentials from earlier development manifests require rebuilding instead of migration.

Remote consent remains machine-local: `authorization.json` identifies its signer, while the signing key stays outside the workspace. A missing or different signing key, or a different workspace root, leaves the workspace unapproved and allows a new grant. A corrupt grant signed by this machine remains an error. Copying workspace credentials never transfers consent to send data.

File IDs remain unchanged while a record is updated, renamed at the workspace level, or relocated with its index. Deleted IDs are never reused within that generation, including after reopening. Rebuilds can assign different IDs. Both entity identities and generation metadata remain internal. Directory filters use indexed arrays of `u32` directory IDs on file and search documents. The `directories` collection stores directory ID, parent ID and native path; memory maps accelerate lookup.

## Canonical data and content-kind indexes

Each generation contains three shared collections: `directories`, `files`, and `entities`. Each entity stores its original content once, its `source_range` within the file, and every one of its globally unique fragments. A fragment contains only an independent ID and a `range` relative to the entity content. Both locations use the same `Range` type. An entity source location can be `Full`, `Text` with complete text coordinates, or `Byte`. A fragment uses `Full` for the entire content or `Byte` with only `start_offset` and `end_offset` in the entity's decoded UTF-8 text. Partial text fragments never store lines or columns; images require `Full`. Fragment source locations are derived from the entity's source range and the fragment's relative range; no second coordinate system is stored on a fragment. Fragments have no content, file, owner, or metadata copy. The canonical entity record stores the complete fragment definitions, with metadata stored once in its own field. There are no representative or standalone fragment variants. Composite content is reserved as a future explicit extension; ordinary entities cannot contain a list of unrelated contents.

The workspace descriptor stores a resolved default model and explicit content-kind overrides. Effective table definitions are derived from these settings, without a second model-reference mapping. An override must support its kind. The default enables only kinds it supports. Each entity is embedded by its kind's model; compatible requests can share batching and model runtimes across kinds.

Every enabled kind has its own `fragments_text`, `fragments_code` or `fragments_image` collection. Text/code tables hold fragment text, FTS, vectors, canonical IDs and filtering fields; image tables omit FTS. The kind identifies the table and its model is configuration. Search verifies that each returned fragment belongs to its canonical entity.

`--embedding model` selects the default model; `--embedding kind=model` sets an override, and `--embedding kind=default` removes it to inherit the workspace default. Independent PNG, JPEG and static WebP files become image entities containing their encoded source bytes. Content unsupported by its selected model is skipped before extraction or embedding. Changing the enabled tables, model provider/name, vector dimension or metric requires explicit `zg --index --rebuild`. Endpoint, input limit, runtime credential, concurrency and timeout changes do not require rebuilding; supported content kinds are validated against each enabled table.

Queries preserve their input kind independently of an optional target kind. An explicit target searches only that table using its model; an omitted target searches every enabled table whose model supports the query's input kind for vector search. Query vectors can be reused for identical model and encoding configurations. Only comparable pure-vector scores share a ranked group; full-text, hybrid and incompatible vectors retain independent kind rankings. Search results expose paths and previews; there is no public snapshot-reading interface.

## Index compatibility

`WorkspaceManifest` combines a domain `Workspace` with persistence-specific fields: workspace home, index version, active storage generation, and embedding runtime configuration. It does not embed an API `WorkspaceIndexInfo`.

`indexVersion` covers the manifest, storage schema and index construction rules, including built-in model weights, content preprocessing and chunking. Incompatible changes require a version bump; query-only encoding changes do not. The current unreleased Rust version remains 2; Node.js indexes use version 1. The manifest records resolved `defaultEmbeddingModel`, `embeddingRoutes` and runtime configurations, alongside source selection settings. Storage records effective kind-table definitions. Loads validate the root, model consistency, route capabilities and storage generation, then compare the manifest's effective tables with storage. Structural validation still rejects corrupt current-version data; it does not maintain another version counter.

Inspection determines compatibility before decoding current-format metadata or opening storage. Missing or different versions and invalid persisted metadata report `rebuild_required`, including actual and expected versions and the reason. Search, incremental indexing, and watcher activation reject that state. An unbuilt workspace remains distinct from incompatible persisted data. An explicit rebuild starts with the requested embedding model or the configured default and new scan settings; it does not migrate an incompatible manifest. Prior Rust development formats do not need migration support.

The current index lives at `.zvec-grep/index/`. Its generation UUID is manifest metadata, not a directory name. Ordinary incremental indexing updates this index in place. File replacements hide incomplete projections until the file is committed, so readers never mix old and new fragments. Unfinished file records remain available for recovery. Incremental updates do not create immutable generations or another compatibility version.

## Publication and recovery

First builds and rebuilds start in empty storage at `.zvec-grep/temp/new-index/`. `temp/build.json` records the new generation, workspace registration, original manifest fingerprint, and whether publication has begun. Completed storage handles close before publication. Under the workspace write lock, the previous `index/` moves to `temp/old-index/` and the new index moves into `index/`; an atomic replacement of the root manifest commits the new generation. Directory moves are flushed before that commit. Successful publication removes the old index and temporary state. Cleanup failures leave the record for a later writer to retry.

Before the manifest commit, crash recovery restores the previous index (or removes an unpublished first index); after the commit it only finishes cleanup. Reader admission acquires the write lock and drains cached handles when an interrupted publication needs recovery, so readers never pair an old manifest with a new index. Recovery and cleanup are repeatable after interruption, and paths remain relative to the workspace after relocation. An explicit rebuild always starts a fresh attempt. Per-file extraction or embedding failures are recorded without preventing publication of successful files; cancellation, storage mutation failure, or failure to close storage preserves the previous index. No previous Rust development layout is migrated.

The indexing application service acquires the workspace lock before changing metadata and storage. After successful publication it updates the optional registry under a separate lock. Storage is organized by table: `directories`, `files`, `entities`, and `fragments` own their schemas, codecs, and collection operations. `IndexStore` holds the shared leases and locks and coordinates cross-table writes, file status transitions, and search-result loading. The file ID cache belongs to the file table; these mechanisms remain separate from workspace naming.

## Persisted state and runtime observations

`Workspace.index` is `Uninitialized`, `Disabled`, or `Enabled(IndexDescriptor)`. Enabled always carries the embedding model information, default and routing configuration, and fixed FTS configuration; physical paths and publication remain owned by the workspace persistence layer. A first build or rebuild keeps its target in `WorkspaceBuild` until publication. The selected descriptor does not imply that files are up to date or that every file succeeded. Content kind determines an entity's model, while file completion covers all of its entities.

The daemon's `WorkspaceRuntime` holds an optional `IndexStatusSnapshot`: observed health, file statistics, and inspection time. No snapshot means unchecked or invalidated. Watcher changes, indexing submissions and completions (including failure/cancellation), and drop invalidate it. Epoch and job checks reject scans overlapping these changes. Runtime snapshots can read this memory without scanning; explicit CLI/MCP status still reads disk and refreshes the observation. Watchers may miss external changes, so an observation is not a lasting freshness guarantee. Restart starts without an observation.

`IndexStats` contains counts and a `failed_files` list with paths and reasons; `IndexResult` also reports failed files. `IndexStatus` distinguishes unknown, uninitialized, disabled, missing, ready, stale, and failed. Queued/running/cancelled build states remain in the scheduler. CLI readiness requires a completed check with no failed, pending, added, modified, or deleted files.

FTS currently uses the fixed `FTS_CONFIG` (`jieba` tokenizer and `lowercase` filter). The same constant configures native storage and populates `IndexDescriptor` when creating or reading a workspace. It is not user-configurable or separately persisted; changes belong to the physical index format. Index info exposes it through the engine API, daemon protocol, CLI status, and MCP status.

## File failure semantics

All embedding inputs belonging to a file finish before any replacement is submitted. A successful replacement publishes the complete file. A file preparation or embedding failure removes all prior entities and all kind-table projections for that file, retains its file record with a failure reason, and makes it eligible for a complete retry. Failed files have no searchable stale or partial records. A model batch can contain several files, but each file is committed or failed independently.

File replacement first persists `NotIndexed`, replaces and flushes entities and kind-table projections, then publishes `Indexed`. Deletion first persists `Deleting`, removes and flushes related records, then removes the file record. There is no separate pending journal or automatic recovery on open. Each indexing run includes unfinished files even outside an incremental change scope; missing or excluded sources are removed, and deleting records finish deletion. Failed records retain the normal retry policy. Directories are shared immutable identities and unused directories are retained.

Search excludes unfinished files before each table's top-k selection. Missing file, entity, or fragment references are skipped, while malformed records and storage failures return errors. Writer locks protect mutation, and checkpoints flush accepted writes. Rebuild publication commits the generation through an atomic manifest replacement, and successful publication may include failed file records.
